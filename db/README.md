# 운영 DB 에 골프올인원 판을 올리는 차례 (2026-11-13 확정)

⚠️⚠️⚠️ **이 Supabase 프로젝트에는 다른 서비스가 같이 살고 있습니다.**
`public` 에 정육 · 창업 상담 서비스의 표 **16개**가 **실데이터와 함께**
들어 있습니다(글 90 · 댓글 99 · 상품 14 · 상담 4). 아래 차례는 그 열여섯과
그 데이터 · 권한 · 정책을 **한 줄도 건드리지 않습니다** — 올린 뒤
`db/post-apply.sql` 이 그것을 그 자리에서 확인해 보여 줍니다.

⚠️⚠️ **표 이름은 하나도 겹치지 않습니다.** 우리가 만드는 표 59 · 보기 37 ·
함수 231 · 타입 14 를 그 열여섯과 맞춰 보았고 **충돌 0건**입니다
(`listing` ↔ `listings` · `jobpost` ↔ `jobs` 처럼 비슷하지만 다릅니다).
그래서 **새 프로젝트를 만들 까닭이 없습니다.**

### 0단계로 확인한 것 (2026-11-13 · `check-evt.sql` 결과)

| 물은 것 | 확인된 값 | 올리는 데 미치는 영향 |
|---|---|---|
| 이벤트 트리거 | `ensure_rls` — `ddl_command_end` · `CREATE TABLE · CREATE TABLE AS · SELECT INTO` · 임자 postgres · 켜짐 → `rls_auto_enable` | **표를 만들 때마다 RLS 를 켭니다.** 우리 마이그레이션도 59개 전부 켜므로 같은 일을 두 번 하는 것이고 서로 부딪히지 않습니다 |
| `rls_auto_enable` 정의 | `security definer` · `search_path = pg_catalog` · `public` 스키마만 · `alter table if exists … enable row level security` · **`exception when others` 로 감싸 로그만 남기고 넘어갑니다** | **우리 마이그레이션을 멈출 수가 없습니다.** 실패해도 그 트리거가 조용히 넘어갑니다 |
| 그 함수의 실행 권한 | anon · 회원 모두 `true` | **해롭지 않습니다** — `returns event_trigger` 인 함수는 Postgres 가 직접 호출을 거부합니다 |
| 기존 16개 표의 정책 역할 | 대부분 **PUBLIC(anon 포함)** · `jobs` · `purchase_requests` · `suppliers` 는 `anon` 에게 **ALL** | 우리가 건드리지 않습니다. 다만 그 상태를 보고에 적습니다 |
| 확장 | `pgcrypto 1.3` 이 **`extensions` 스키마**에 이미 설치 · `uuid-ossp` 도 | **0063 이 그대로 돕니다** — `create extension if not exists` 가 no-op 이고, 그 파일의 함수는 `search_path = public, extensions` 라 `crypt()` · `digest()` 를 찾습니다 |
| realtime publication | `supabase_realtime` · **고른 표만 · 0개 표** | **우리 표 59개가 realtime 에 저절로 안 들어갑니다** |

⚠️ 그래서 올리기 전에 **DB 쪽에서 더 알아볼 것이 없습니다.** 남은 것은
1단계부터 차례대로 붙여 넣는 일입니다.

### 왜 1 · 7 단계가 필요한가 — 재서 확인한 것

이 프로젝트는 `public` 에 새로 생기는 **표**와 **함수**를 anon · 회원에게
**직접** 열어 주도록 설정되어 있습니다(Supabase 의 기본값 · survey ⑪).
그대로 올리면 —

* 마이그레이션의 `revoke … on function … from public` **200곳**이 무력화되어
  내부 함수 **31개**가 전부 열립니다(그중 `notify_one` 은 아무에게 아무
  제목으로 알림을 꽂을 수 있습니다 — 0050 머리말의 그 구멍입니다).
* 칸 단위 GRANT 가 **11개 표**에서 풀려 `contact`(동의 전 연락처 ·
  제17조 제2항) · `teebook.tel` · `notice.to_user` 가 읽힙니다.
* 표 **20개**에 표 단위 권한이 붙습니다(RLS 가 줄은 막지만 자물쇠 한 겹이
  사라집니다).

운영과 **같은 기본 권한**을 임시 Postgres 에 재현해 재 보았습니다 —
`pre-apply` 없이 **31/31 열림**, `pre-apply` 뒤 **0/31**. 그리고
`pre-apply` 를 거친 DB 의 우리 객체 권한은 **검사용 DB 와 완전히 같습니다**
(객체 327개 전부 일치) — 즉 `node tools/test-sql.js` 가 재는 것이 그대로
유효합니다.

### 1-3. 돌린 다음 반드시 확인할 것

⚠️⚠️ **`db/verify.sql` 을 통째로 붙여 넣고 Run 하세요** — 열세 가지를

⚠️⚠️⚠️ **기대값(판 · 표 · 함수 …)을 여기 옮겨 적지 않습니다.** 2026-11-10

⚠️⚠️ **아직 `0008` 부터를 안 돌리셨으면 판 · 표 · 함수 셋이 ❌ 로 나옵니다** —
그건 "DB 가 망가진 것" 이 아니라 **§1-2 의 붙여넣기 파일을 돌리시면 되는

(정책을 손댔거나 · 권한을 줬거나).

⚠️⚠️ **`tools/test-sql.js` 는 가짜 auth 스키마로 돕니다** — 진짜
Supabase 에서만 드러나는 둘(**auth.users 트리거** · **auth.uid()**)은
`verify.sql` 의 ⑧ ⑨ 가 봅니다. 그 둘이 ❌ 면 로그인은 되는데 역할이
안 생기거나, 상태를 바꾸는 모든 문이 "변경자를 모릅니다" 로 거절합니다.

아래 다섯은 그중 급한 것을 따로 적어 둔 것입니다.

```sql
-- ① ⚠️ 판 번호가 **마지막 번호까지** 들어왔는가
--    (몇 줄이어야 하는지는 `ls db/migrations | wc -l` 이 말해 줍니다)
select * from schema_version order by n;

-- ② ⚠️⚠️ RLS 가 안 켜진 표가 하나라도 있는가 — 0건이어야 합니다
select tablename from pg_tables t
  join pg_class c on c.relname = t.tablename
 where t.schemaname = 'public' and c.relrowsecurity = false;

-- ③ 상태값이 **열셋**인가 — 보류(hold)가 들어 있어야 합니다
--    (js/data/deal.js 의 AM_DEAL_ST 와 같아야 합니다)
select unnest(enum_range(null::deal_state));

-- ④ ⚠️⚠️ 돈 칸에 로그인 사용자 쓰기 권한이 없는가 — 0건이어야 합니다
select column_name from information_schema.column_privileges
 where table_name='deal' and grantee='authenticated' and privilege_type='UPDATE'
   and column_name in ('fee','fee_total','fee_snap','paid');

-- ⑤ ⚠️⚠️ 감사 기록을 고치거나 지우는 정책이 없는가 — 0건이어야 합니다
select policyname from pg_policies
 where tablename='audit_log' and cmd in ('UPDATE','DELETE','ALL');
```

⚠️ ②가 한 줄이라도 나오면 **멈추고 그 표에 RLS 를 켜세요.**
`tools/check-deal.js` 가 SQL 파일에서 그것을 보지만, **실제로 돌아간
DB** 는 사장님이 ②로 확인하셔야 합니다.

### 1-4b. ⚠️⚠️ 「자체 매입 부서」 절은 **걷어냈습니다** (2026-11-10)

- `insert into provider ... '폰웨이 매입팀'` — 골프 사이트에 **앞 서비스
  회사 줄을 심는** SQL 입니다(절대 규칙 1 · 표시광고법 제3조).

⚠️ 앞 서비스를 되살리실 때 필요하시면 `git show 4563539:db/README.md`

### 1-4c. ⚠️⚠️⚠️ 소셜 로그인으로 바꾸시는 날 — **관리자가 잠깁니다**

카카오 · 네이버 · 구글을 켜고 **이메일 입력창을 지우시면, 그 순간
`/admin` 에 들어갈 길이 사라집니다.** 까닭은 한 줄입니다 —

```
my_role()  =  select role from account where id = auth.uid()
```

운영자 권한은 **특정 계정 하나(`auth.uid()`)** 에 붙어 있습니다. 지금
관리자 계정은 **메일로 만든 계정**이고, 카카오로 들어오시면 Supabase 가
**새 uid** 를 만듭니다. 그러면 `0005_account_claim.sql` 의 트리거가 그
줄을 **`customer`** 로 넣습니다 — 카카오가 이메일을 안 주니 두 계정을
이을 열쇠가 없습니다.

⚠️⚠️ **차례를 지키시면 안 잠깁니다. 하나라도 건너뛰지 마세요.**

**① 소셜로 한 번 로그인하십니다**

`/login` 에서 카카오(또는 켜신 것)를 눌러 **끝까지 들어오십니다.**
이때 새 계정이 만들어집니다.

**② 그 계정의 user id 를 찾습니다**

Supabase → **Authentication → Users** 에서 방금 들어온 줄을 보시거나,
SQL Editor 에서 —

```sql
select u.id, u.email, i.provider, u.created_at
  from auth.users u
  left join auth.identities i on i.user_id = u.id
 order by u.created_at desc
 limit 10;
```

`provider` 가 `kakao` 인 **가장 최근 줄**이 방금 만드신 계정입니다.

⚠️ 이 SQL 은 Supabase 가 제 안에 두는 `auth` 스키마를 읽습니다 —
저희 검사용 Postgres 에는 그 스키마가 없어 **돌려 보지 못했습니다.**
칸 이름이 다르다고 거절당하면 그냥 **Authentication → Users** 화면에서
눈으로 찾으세요(그게 더 빠릅니다).

**③ 그 계정을 관리자로 올립니다** (§1-4 와 같은 한 줄)

```sql
update account set role = 'admin' where id = '<②에서 찾은 user id>';
```

**④ `/admin` 이 열리는지 눈으로 확인합니다**

열리면 끝입니다. **안 열리면 ③의 id 가 다른 줄입니다** — ②를 다시
보세요.

**⑤ 그다음에야** 이메일 입력창을 지웁니다.

⚠️⚠️ **옛 메일 계정은 당분간 그대로 두십니다.** 이메일 칸을 지우기
전까지는 들어올 수 있는 **되돌아갈 길**입니다. 소셜 로그인이 며칠
멀쩡히 돈 뒤에 내리셔도 늦지 않습니다 —

```sql
-- ⚠️ 급하지 않습니다. ④까지 확인하고 며칠 지켜본 뒤에.
update account set role = 'customer' where id = '<옛 메일 계정 id>';
```

⚠️ **관리자를 화면에서 만들 수 있게 하지 않는 규칙은 그대로입니다**
(§1-4). 역할 올리기는 **SQL 로만** 합니다 — 그래서 이 걸음이
사장님 손으로 남아 있는 것입니다.

⚠️⚠️ **같은 분이 공급자마다 다른 계정이 됩니다.** Supabase 가 계정을
잇는 잣대는 **확인된 이메일**인데, 카카오에서 이메일을 안 받으면 이을
열쇠가 없습니다. 카카오로 들어오신 분이 다음에 구글로 들어오시면
**다른 계정**이고, 앞서 올린 글 · 매물이 그 계정에는 없습니다.
못 막는 것을 막는다고 적지 않습니다 — 받아들이시려면 그대로 두고,
막으시려면 카카오에서 **이메일을 필수 동의**로 받으셔야 합니다
(비즈 앱 전환 · 사업자등록번호가 필요합니다).

## 2. 판 번호 — 마이그레이션 규칙

```
db/migrations/NNNN_이름.sql        ← 올리는 것
db/migrations/NNNN_이름_down.sql   ← 되돌리는 것 (있으면)
```

- ⚠️ **번호를 다시 쓰지 마세요.** 이미 돌린 파일을 고치지 말고 **다음
  번호로 새로** 만듭니다. 고치면 "내 DB 가 그 수정 전인지 후인지" 를
  알 방법이 없어집니다.
- ⚠️ 새 파일마다 `schema_version` 에 한 줄을 **같이** 넣으세요
  (`0002` 가 그 예입니다).
- ⚠️⚠️ **되돌리기 파일은 전부 주석으로 막아 두었습니다.** 통째로
  돌아가는 되돌리기 파일은 언젠가 실수로 운영에서 돌아갑니다.
  지우실 것만 골라 주석을 푸세요.

### 바꾸기 전에 보는 것

| 바꾸려는 것 | 위험 | 하는 법 |
|---|---|---|
| 칸 **추가** | 낮음 | `alter table … add column … null` (기본값 null) |
| 칸 **이름 변경** | ⚠️⚠️ 높음 | 바꾸지 말고 **새 칸을 더하고** 옮긴 뒤 옛 칸을 나중에 지웁니다 |
| 상태값 추가 | ⚠️ 중간 | `alter type deal_state add value …` + **`js/data/deal.js` 를 같이** (빌드가 맞춰 봅니다) |
| 상태값 **삭제** | ⚠️⚠️ 높음 | Postgres 는 enum 값을 못 지웁니다. 쓰지 않는 상태로 두세요 |
| 수수료 정책 변경 | ⚠️⚠️ 높음 | **지난 계약은 사본(`deal.fee_snap`)을 씁니다** — 정책을 고쳐도 안 바뀝니다 (§9). 그게 맞습니다 |
| RLS 정책 변경 | ⚠️⚠️ 높음 | 바꾼 뒤 **역할마다 실제로 로그인해서** 남의 것이 안 보이는지 확인 |

## 3. 백업 · 복구 (§1)

### 3-1. 저절로 되는 것

Supabase 가 자동 백업을 해 줍니다. ⚠️ **보관 기간과 시점 복구(PITR)가
요금제마다 다릅니다** — 가입하신 뒤 대시보드에서 **실제 보관 기간을
확인하고 아래 빈칸을 채워 주세요.**

```
자동 백업 보관 기간 : ______ 일   (대시보드에서 확인)
시점 복구(PITR)     : 되는가? ______
```

⚠️ 확인하지 않고 "백업이 되고 있다" 고 믿는 것이 가장 위험합니다.
이 저장소가 접수처를 "켰습니다" 로 몇 주 거짓으로 적어 둔 적이 있습니다.

### 3-2. 손으로 뜨는 것 — **큰일 전에는 반드시**

마이그레이션을 돌리기 **직전**, 그리고 **정산을 돌리기 직전**에.

```bash
# 전체 (스키마 + 데이터)
pg_dump "$DB_URL" -Fc -f backup-$(date +%Y%m%d-%H%M).dump

# ⚠️⚠️ 돈과 기록만이라도 (제일 되돌릴 수 없는 것들)
pg_dump "$DB_URL" -Fc -t deal -t fee_policy -t settlement -t audit_log \
  -f money-$(date +%Y%m%d-%H%M).dump
```

- ⚠️⚠️ **받은 덤프 파일을 저장소에 넣지 마세요.** 손님 성함과 연락처가
  들어 있습니다. 공개 저장소입니다.
- ⚠️ 덤프 자체가 개인정보입니다 — 보관 장소와 기간을 정하고 **지나면
  지우세요** (제21조).

### 3-3. 복구

```bash
# ⚠️⚠️ 운영에 바로 넣지 마세요. 새 프로젝트에 먼저 복구해 보고,
#      ①판 번호 ②RLS ③건수 셋을 확인한 뒤에 옮깁니다.
pg_restore -d "$NEW_DB_URL" --clean --if-exists backup-….dump
```

복구한 뒤 반드시 —
1. `select * from schema_version order by n;` — 판 번호가 맞는가
2. 위 1-3 의 ② — **RLS 가 전부 켜져 있는가** (복구에서 빠지기 쉽습니다)
3. `select count(*) from request; select count(*) from deal;` — 건수가 맞는가
4. 역할마다 로그인해서 **남의 것이 안 보이는지**

### 3-4. ⚠️⚠️ 한 달에 한 번은 **복구를 해 보세요**

떠 보기만 하고 넣어 본 적 없는 백업은 백업이 아닙니다. 새 프로젝트에
덤프를 넣어 보고, 위 네 가지를 확인한 뒤 그 프로젝트를 지우면 됩니다.

## 4. 이 폴더가 지금 지키는 것

| 무엇 | 어디 |
|---|---|
| 화면의 **상태 말**이 DB 의 enum · check 와 같다 | `tools/check-deal.js` — 다르면 **빌드가 멈춥니다** (⚠️ 세는 묶음은 늘어납니다 — 여기 적지 않습니다) |
| 표마다 **RLS 가 켜져 있다** | 같은 검사 (SQL 파일 기준) |
| 감사 기록을 **고치거나 지울 수 없다** | 같은 검사 + RLS 에 update·delete 정책이 없음 |
| 수수료 확정이 **관리자 전용이다** | `checkDeal()` · `deal_money_guard()` 트리거 |
| 수수료가 적혔으면 **승인자와 시각이 있다** | `deal_fee_needs_approval` 제약 |
| 입금액이 적혔으면 **수수료가 먼저 확정돼 있다** | `deal_paid_needs_fee` 제약 (§13) |
| 배정에 **제3자 제공 동의 시각이 있다** | `assignment.agree3rd_at not null` (제17조 제2항) |
| 업체가 **확인 배지를 스스로 못 켠다** | `provider_guard()` 트리거 (절대 규칙 1) |
| 업체 주소(id)를 **못 바꾼다** | 같은 트리거 (이미 색인된 주소) |

⚠️ 되돌려 봤습니다 — SQL 의 상태값 하나를 바꾸고 · RLS 한 줄을 지우고 ·
감사 기록에 수정 정책을 넣고 · 업체가 수수료를 확정할 수 있게 하고 ·
계약완료에서 정산으로 바로 가는 길을 만들어 보니 **다섯 다 빌드가
멈췄습니다.**
