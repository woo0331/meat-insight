# 0022 — 앞 서비스 접수를 **지우지 않고** 내려놓습니다

> 2026-11-02 · 전환 지시서 §6 — *"기존 운영 데이터를 삭제하거나 임의로
> 변경하지 않는다 … 삭제 작업은 가능한 경우 복구 가능한 마이그레이션으로
> 관리한다."*
>
> 사장님 지시 — **"0022마이그레이션 써줘"** · **"1번"**
> (`request.side` 의 앞 서비스 값 넷만, `industry` 는 건드리지 않기).

## 한 줄로

```
지운 것      없습니다 (칸 · 줄 · 기록 전부 그대로)
더한 것      request.archived_at · archived_why  +  문 둘
바뀐 화면    api/me.js 목록 질의 한 줄 (archived_at=is.null)
운영에 미치는 영향   0 — 문을 **부르기 전에는 한 줄도 안 움직입니다**
```

## 1. 왜 "보관 표로 옮기기" 를 버렸나

처음 계획(이 저장소의 CLAUDE.md 가 적어 두었던 것)은 옛 접수를 **접근이
제한된 보관 표로 옮기는** 것이었습니다. 쓰기 전에 재 보니 —

```bash
grep -n "references request(id)" db/migrations/*.sql
```

| 표 | 외래키 |
|---|---|
| `assignment` (0001:168) | `on delete cascade` |
| `deal` (0001:224) | `on delete cascade` |
| `quote` (0008:49) | `on delete cascade` |
| `request_item` (0009:71) | `on delete cascade` |
| `request_photo` (0011:55) | `on delete cascade` |
| `device` (0020:44) | `on delete set null` |

**줄을 옮긴다는 것은 `request` 에서 지운다는 뜻**이고, 그러면 그 건의
배정 · 계약 · 수수료 · 입찰 · 사진이 **같이 사라집니다.** §8 이 "모든
중요한 상태 변경을 기록한다" 고 정해 둔 그 기록이 통째로 없어지는 것이라,
복구 가능한 마이그레이션이 아니라 **제일 비싼 파괴**였습니다.

**스냅샷 보관 표도 만들지 않았습니다.** 옛 줄을 베껴 두면 성함 ·
연락처가 **두 번 보관**됩니다 — 이 저장소가 `note_request_open` ·
`save_provider_contact` 에서 "기록은 못 지우는 것이라 그 자체가 또 하나의
보관입니다" 로 두 번 적어 둔 자리입니다. 원본 줄이 그대로 남아 있으니
베낄 까닭도 없습니다.

## 2. `request.industry` 는 **구사업 칸이 아니었습니다**

CLAUDE.md 의 "승인 대기" 표가 그 칸을 구사업 흔적으로 적어 두었는데,
`grep` 으로 세 보니 **뜻이 바뀐** 칸입니다 — 지금 중고폰 **기기 종류**를
담고 `api/me.js` 의 `PICK` 넷(고객 · 업체 · 직원 · 한 건 열기)이 전부
가져갑니다. `js/pages/my.js` 의 조건 줄과 `js/intake.js` 의 거르개가 그
값을 읽습니다.

지우면 PostgREST 가 없는 칸을 달라고 해서 **`/my` 와 `/admin` 접수
목록이 통째로 안 그려집니다** — 그래서 0022 는 그 칸을 **한 글자도 안
건드립니다.** 그 표의 줄은 지금 고쳤습니다.

## 3. 무엇이 생겼나

### 칸 둘

```sql
alter table request add column if not exists archived_at  timestamptz;
alter table request add column if not exists archived_why text;
constraint request_archived_why_ok
  check (archived_at is null or btrim(coalesce(archived_why,'')) <> '');
```

- **쓰기 권한을 주지 않습니다.** 0001 의 GRANT 가 칸 단위라 안 더하면
  그대로 닫혀 있습니다 — 바꾸는 길은 아래 문 둘뿐입니다
  (`verified` · `listed` · `inhouse` 와 같은 선).
- **사유 없는 보관은 기록이 아닙니다** (§8). 시각만 찍히고 왜
  내려놓았는지가 없으면 반 년 뒤에 "이게 왜 목록에 없지" 를 아무 데서도
  못 읽습니다 — 0014 의 `request_notify_at_ok` 과 같은 제약입니다.

### 문 둘 (둘 다 관리자만 · 둘 다 감사 기록을 같은 트랜잭션에서)

| 문 | 무엇 | 막는 것 |
|---|---|---|
| `archive_legacy_side(사유)` | `side in ('start','ops','transfer','close')` 를 한 번에 내려놓습니다 | 로그인 없음 · 관리자 아님 · 사유 없음 · **돈이 안 끝난 건** |
| `restore_legacy_request(신청번호, 사유)` | **한 건**을 되돌립니다 | 같은 넷 + 못 찾음 (한 가지 말로만) |

`archive_legacy_side()` 는 `{"archived": n, "kept": m}` 을 돌려줍니다.

### ⚠️⚠️ 돈이 안 끝난 건은 두고 갑니다

수수료를 확정해 두고 입금이 안 된 건(`deal.fee_at` 이 있고 `paid_at` 이
비었음)을 목록에서 내리면 **미수금이 화면에서 사라집니다** — §13 이
금지한 가짜 정산과 결이 같습니다. 그런 건은 **세어서 `kept` 로
돌려주고** 사람이 먼저 정산하게 둡니다.

**두고 온 수를 같이 돌려주는 까닭** — 내려놓은 수만 내면 "다 됐다" 로
읽히고, 남은 건은 아무도 안 봅니다.

### 되돌리는 문이 **한 건씩**인 까닭

통째로 되돌리는 문을 만들면 잘못 누른 날 손볼 자리가 없습니다. 전부
되돌리시려면 파일 머리말의 `update` 한 줄이고, 그건 사람이 한 번 더
생각하고 치는 길입니다.

**없는 번호와 안 보관된 번호를 갈라서 말하지 않습니다** — 갈라 주면
번호가 있는지를 확인해 가며 긁을 수 있습니다 (0005 의 `claim_request` 와
같은 까닭).

## 4. 화면이 **안 읽으면 보관은 아무 일도 안 합니다**

```js
// api/me.js — 역할 넷이 같이 쓰는 목록 질의
"?select=" + encodeURIComponent(pick) +
"&archived_at=is.null" +
"&order=created_at.desc&limit=" + LIMIT
```

- **역할을 가르지 않았습니다.** 고객 쪽만 내리면 직원 목록에 앞 서비스가
  그대로 쌓여 있고, 직원 쪽만 내리면 410 으로 닫은 서비스를 여전히
  고객에게 보여 주는 것이 됩니다.
- **한 건을 여는 길은 그대로입니다** (`?r=<id>&c=1` · `id=eq.`) —
  되돌리기 전에 관리자가 그 건을 봐야 합니다.
- 빌드 가드가 **거르는 글자 그대로**(`archived_at=is.null`)를 셉니다.
  처음에 `archived_at` 만 찾았더니 **바로 위 주석에 그 낱말이 있어서**
  거르는 줄을 지워도 그냥 통과했습니다 (되돌려 보고 알았습니다).

(`{"archived": 0, "kept": 2}`)을 실패로 잡았습니다.

## 6. 사장님께 — 지금 하실 일과 **하지 마실 일**

### 하실 일

`db/apply-from-0008.sql` 이 이제 **0008~0022 열다섯 개**입니다. 아직
안 돌리셨으면 그 파일 하나를 통째로 붙여 넣으시면 되고, 이미 0021 까지
돌리셨으면 **`0022_legacy_archive.sql` 만** 따로 돌리시면 됩니다.
그 뒤 `db/verify.sql` 열세 줄이 전부 ✅ (기대값 **판 22 · 표 21 ·
함수 48**).

### ⚠️⚠️ 하지 마실 일 — `archive_legacy_side()` 를 **아직 부르지 마세요**

§6 이 **백업과 복구 확인을 먼저**라고 적었고, 그건 이 작업 환경에서
제가 닿을 수 없는 일입니다 (운영 Supabase 에 못 들어갑니다).
0022 는 **칸과 문을 세워 두기만** 합니다 — 부르지 않으면 지금과 글자
하나 다르지 않습니다.

백업과 복구 확인이 끝나시면, SQL Editor 에서 한 줄입니다 —

```sql
select archive_legacy_side('앞 서비스(창업 · 폐업) 종료 — 전환 지시서 §6');
```

돌려주는 값이 `{"archived": n, "kept": m}` 입니다. **`kept` 가 0 이
아니면** 그만큼은 수수료를 확정해 두고 입금이 안 된 건이라 두고 온
것입니다 — 먼저 정산하신 뒤 같은 줄을 한 번 더 돌리시면 됩니다.

되돌리실 때는 한 건씩 —

```sql
select restore_legacy_request('SW-XXXX-XXXX', '되돌리는 까닭');
```

⚠️ 둘 다 **관리자 세션**에서만 됩니다 (`auth.uid()` 가 비면 거절합니다 —
변경자를 못 적는 기록은 기록이 아닙니다).
