## 2. 길 A — 골프올인원용 **새 프로젝트**

### 옮겨지는 것 / 안 옮겨지는 것

| 무엇 | 새 프로젝트에서 | 어떻게 해야 하나 |
|---|---|---|
| **Auth 계정(`auth.users`)** | ❌ **하나도 안 따라옵니다** | 프로젝트마다 Auth DB 가 따로입니다. 옮기려면 `auth.users` · `auth.identities` 를 **SQL 로 복원**해야 합니다(Admin API 의 `createUser` 는 **UID 를 지정할 수 없어** UID 가 바뀝니다 → 우리 `account.id` 가 그 UID 를 가리키므로 **반드시 SQL 쪽**) |
| **관리자 UID** | ❌ 위와 같음 | 위를 하면 보존됩니다. 안 하면 **새 UID** 가 되고 기존 글 · 기록과의 연결이 끊깁니다 |
| **비밀번호 · 매직링크** | 해시를 같이 옮기면 유지 | `encrypted_password` 까지 복원해야 기존 이메일 로그인이 그대로 됩니다 |
| **OAuth(카카오 · 구글)** | ❌ **설정이 안 따라옵니다** | 새 프로젝트에서 공급자를 다시 켜고, **카카오 · 구글 콘솔의 Redirect URI 에 새 프로젝트 콜백 주소를 추가**해야 합니다. `auth.identities` 를 안 옮기면 기존 소셜 계정은 **새 계정으로 새로 생깁니다** |
| **Storage 버킷 · 파일** | ❌ 안 따라옵니다 | 버킷을 다시 만들고 파일을 옮깁니다(지금은 버킷이 없으므로 **옮길 것이 0건**) |
| **환경변수** | 교체 | Vercel 의 `SUPABASE_URL` · `SUPABASE_ANON_KEY`(필요하면 `SUPABASE_SERVICE_KEY`)를 새 값으로. **Production 과 Preview 둘 다** 체크해야 합니다 |
| **기존 앱(창업 · 폐업)** | 그대로 | 그 프로젝트를 **한 글자도 안 건드립니다** |

### 되돌리기
Vercel 환경변수를 **바꾸기 전 값으로 되돌리고 재배포**하면 끝입니다
(새 프로젝트는 그냥 남겨 둡니다). 기존 DB 를 안 건드렸으므로 **잃는 것이 없습니다.**

### 언제 고르나
- (나)와 (가)가 **다를 때** — 운영이 쓰는 프로젝트가 따로 있다면 이야기가 달라집니다.
- 기존 앱을 **계속 운영**하실 때.
- 기존 계정이 **거의 없을 때**(⑩ 의 수로 확인). 계정이 0~몇 명이면 옮길 것이 사실상 없습니다.

## 3. 길 B — **같은 프로젝트에 더하기**

### 더해지는 것
표 59 · 보기 37 · 함수 145 · 타입 9. 기존 16표는 **안 건드립니다**(우리 SQL 에
`drop table` · `alter table <남의 표>` 가 없습니다).

### ⚠️ 이름이 안 겹쳐도 위험한 자리 셋

1. **`auth.users` 트리거** — 0005 가 이렇게 돕니다:
   ```sql
   drop trigger if exists on_auth_user_created on auth.users;
   create trigger on_auth_user_created after insert on auth.users ...
   ```
   기존 앱이 **같은 이름**을 쓰면 그 줄이 **남의 가입 처리를 떼어 냅니다**
   (그러면 새로 가입한 사람이 기존 앱의 `members` 에 안 들어갑니다).
   → `db/survey.sql` **⑨** 가 그것을 봅니다. 이름이 같으면 **0005 를 그대로 돌리면 안 됩니다.**

2. **0005 의 메꾸기** — `insert into account select u.id ... from auth.users`
   기존 가입자 **전원**에게 `account` 줄이 생깁니다(역할은 `customer`).
   기존 앱에는 영향이 없지만 **계정 수만큼 줄이 늘어납니다.**

3. **역할 · 권한** — 우리 SQL 은 `anon` · `authenticated` 에게 **우리 표 · 보기 · 함수**에만
   권한을 줍니다. 남의 표 권한은 안 건드립니다. 다만 기존 앱이 `public` 스키마 전체에
   `grant` 를 걸어 두었다면(`grant ... on all tables in schema public`) **우리 표도 그 영향**을
   받습니다 → ⑤ 로 확인합니다.

### 되돌리기
우리가 만든 것만 지우면 됩니다(표 59 · 보기 37 · 함수 145 · 타입 9). 다만
**0005 가 떼어 낸 남의 트리거는 저절로 안 돌아옵니다** — ⑨ 결과를 먼저 저장해 두고,
같은 이름이면 **그 트리거의 정의문을 받아 적어 둔 뒤** 진행해야 합니다.

## 4. 관리자 권한 — 「한 줄 수정」이 충분한가

### 실제로 권한을 판정하는 자리 (코드에서 확인한 것)

| 겹 | 어디 | 무엇을 봅니까 |
|---|---|---|
| ① **DB (진짜 자물쇠)** | `my_role()` — `select role from account where id = auth.uid()` | 정책 · 문 **242곳**이 이것을 씁니다 |
| ② 서버 | `api/_auth.js` 의 `roleOf()` — REST 로 `account.role` 을 읽습니다 | 줄이 없으면 **`customer`**(fail-closed) |
| ③ 화면 | `/api/session` 이 내려준 `role` | **보이기 · 숨기기만** 합니다. 자물쇠가 아닙니다 |

`ADMIN_PASSWORD` 는 `api/admin-health.js` **하나**에만 쓰이고 관리자 판정과 무관합니다.

### ⚠️ 「한 줄」을 막을 수 있는 것 둘

1. **`account_role_guard_t` 트리거**(0021) —
   `provider_id is not null` 인 계정은 `staff` · `admin` 이 **될 수 없습니다.**
   그 계정이 업체에 이어져 있으면 `update` 가 **거절**됩니다.
2. **RLS** — `account` 는 `account_self`(제 줄 select)와 `account_admin`(관리자 전체)뿐이라
   **화면에서는 역할을 못 고칩니다**(GRANT 도 `select` 뿐). SQL Editor 는 임자 권한이라
   RLS 를 지나갑니다.

### 그래서 순서는 이렇습니다 (아직 실행 안 함)
```sql
-- (1) 그 줄이 있고 업체에 안 이어져 있는지 먼저 봅니다 — 조회
select id is not null as 줄있음, role, (provider_id is null) as 업체에안이어짐
  from account where id = '<관리자 UID>';

-- (2) 위가 (있음 / customer / 참) 일 때만 한 줄
update account set role = 'admin' where id = '<관리자 UID>';

-- (3) 실제로 먹었는지 **문으로** 확인 — 그 계정으로 로그인해 /admin 을 엽니다
--     (select 로만 확인하면 트리거 · 정책이 장식인지 알 수 없습니다)
```
⚠️ (2)는 **`provider_id` 가 null 일 때만** 성공합니다. 아니면 먼저 끊어야 합니다
(`drop_provider_staff` · 0052).
