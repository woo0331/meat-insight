# 서버 이미지 전체 해석 — 막힌 것 · 길 · 대안 (2026-11-17)

⚠️ **결정 전입니다.** 이번 배포와 분리하고, **운영 사진을 켜기 전에** 해결하거나 한계를 받아들일지 정해야 하는 항목입니다
(`docs/photo-launch.md` 의 출시 차단 항목과 같은 자리).

## 1. 무엇이 막혔나

- 하려던 일: 공개 npm 패키지 `jpeg-js@0.4.4`(BSD-3, 순수 JS)를 받아 `api/_vendor/jpeg-js/` 에 **복사해 넣고**,
  1600px 사진을 서버에서 전체 해석 · 재인코딩하는 데 걸리는 시간을 재는 것.
- 막힌 까닭: 이 세션의 권한 확인이 **바깥 코드를 저장소에 들여오는 일**을 승인 없이 하는 것으로 보고 거절했습니다.
- **우회하지 않았습니다** — 다른 경로로 같은 파일을 넣거나 돌리지 않았고, 저장소에 아무것도 남지 않았습니다
  (`api/_vendor` 없음을 확인).

## 2. 지금 서버가 하는 것과 그 한계

| 하는 것 | 하지 않는 것 |
|---|---|
| 주인 · 8MB · JPG 만 · 첫 바이트 · 머리(가로 · 세로 · 픽셀 수) · 끝 표시(잘린 파일) · EXIF/XMP · 작은 사진도 같은 검사 | **그림 자료(몸통) 전체 해석** — 머리 · 끝은 멀쩡하고 몸통만 깨지거나 꾸며진 JPG 는 통과합니다(검사에 명시) |

정상 경로(사이트의 사진 칸)는 브라우저가 canvas 로 **전체를 그려 다시 만든** 파일만 보냅니다. 위 한계는
**업로드 주소를 직접 부르는** 경우에만 해당합니다. 0084 를 올리면 그런 파일도 저장 완료 검사를 통과해야 공개됩니다.

## 3. 허용될 수 있는 도입 경로 (전부 승인 필요)

| 길 | 장점 | 단점 · 위험 |
|---|---|---|
| A. `package.json` 에 `jpeg-js` 를 의존성으로 적기 (공식 npm 설치) | 순수 JS · 작음 · 해석 크기 · 메모리 한도 옵션이 있음(`maxResolutionInMP` · `maxMemoryUsageInMB`) · 재인코딩으로 남은 메타까지 지움 | 저장소에 지금 `package.json` 이 **없어** Vercel 빌드에 설치 단계가 새로 생김 · 잠금 파일 · 공급망 관리가 생김 · 순수 JS 라 느릴 수 있음(측정 못 함) · JPG 만 |
| B. `sharp`(libvips) | 빠름 · JPG/PNG/WEBP 전부 · 작은 사진도 서버가 만들 수 있음 | 네이티브 바이너리(수십 MB) · 빌드 · 함수 크기 · 콜드 스타트 증가 · A 와 같은 package.json 문제 |
| C. Supabase 이미지 변환(render) | 코드 거의 없음 | 요금제 기능 · **검증이 아니라 변환**이라 나쁜 파일을 거르는 자리가 아님 |
| D. 지금 그대로 (머리 · 끝 검사 + 브라우저 해석) | 바깥 코드 없음 · 이미 검사됨 | 직접 호출로 몸통이 깨진/꾸며진 JPG 가 공개될 수 있음 — 보는 쪽 브라우저가 해석에 실패해 깨진 그림으로 보이는 것이 대부분의 결과 |

권하는 순서: 운영 사진을 켜기 전에 **A 를 승인받아 도입**하거나, 아니면 **D 를 위험으로 받아들인다고 명시**합니다.

## 4. 승인 요청 (A 를 고르실 때 이 문장 그대로)

> 저장소에 `package.json` 을 새로 만들고 공식 npm 패키지 `jpeg-js@0.4.4`(BSD-3-Clause) 하나를 의존성으로 추가하는 것을 승인합니다.
> 용도는 `api/upload.js` 의 매물 사진 저장 완료 검사에서 JPG 전체 해석 · 재인코딩(해석 한도 5MP · 64MB)이며,
> Vercel 빌드에 의존성 설치 단계가 생기는 것을 이해합니다. 운영 사진 활성화는 이와 별도로 승인합니다.
