# 휴대폰(PASS 본인확인) 로그인 — 연동 준비 (2026-11-15)

**상태: 준비 문서 · 운영에는 카카오 로그인만 있습니다.** 작동하지 않는 휴대폰 로그인
단추는 내지 않았습니다(절대 규칙 5). 이 문서는 사장님이 본인확인 업체를 고르시는 날
바로 들어갈 수 있게 **무엇이 필요하고 어떻게 잇는지**를 정리한 것입니다.

## 1. 지금 저장소

- 본인확인 연동은 **하나도 없습니다** (PortOne · NICE · KCB · 다날 · PASS 흔적 0건).
- `js/auth.js` 의 `/auth/v1/otp` 는 **메일 링크**입니다(휴대폰 SMS 가 아닙니다).
- 약관 제10조가 「본인확인기관을 통해 확인한 정보」를 **말로만** 적고 있습니다(분쟁 때 내는 자료 · 제20조의4).

## 2. PASS 본인확인 ≠ SMS 인증

| | SMS 인증(OTP) | PASS 본인확인 |
|---|---|---|
| 증명하는 것 | 그 번호를 **지금 쥐고 있다** | 그 번호의 **명의자가 이 사람이다** |
| 받는 값 | 전화번호뿐 | 연계정보(CI) · 중복가입확인정보(DI) · 성명 · 생년월일 · 성별 · 통신사 · 전화번호 |
| 누가 하나 | 문자 발송사(Supabase 휴대폰 로그인 + Twilio 등) | **본인확인기관**(통신3사 PASS · NICE · KCB 등)과 계약한 대행사 |
| 같은 사람 판별 | 번호가 바뀌면 다른 사람 | **CI** 로 판별(번호가 바뀌어도 같음) |

⚠️ 목표는 **PASS 본인확인**입니다. Supabase 의 휴대폰 로그인(SMS OTP)으로는 이 목표가 안 채워집니다.

## 3. 연동 구조 (검토안)

```
① 화면   「휴대폰으로 로그인」 → 대행사 인증창(대행사 SDK) → 결과 id 를 받음
② 서버   api/identity.js 가 그 id 로 대행사 API 에 **서버 키로** 결과를 물음
          · 성공 · 시각(몇 분 안) · 한 번만 쓰임(state) 확인 — 화면이 보낸 이름 · 번호는 안 믿음
③ 회원   CI 를 서버 비밀값으로 HMAC → ci_hash
          · ci_hash 가 있으면 그 회원, 없으면 Supabase Admin API 로 새 회원
④ 세션   새 회원 · 기존 회원 모두 **GoTrue 세션**을 받아 화면에 돌려줌
          (화면은 지금처럼 amAuthSave 로 담음 — 받는 자리를 새로 안 만듦)
```

⚠️⚠️ **④가 가장 큰 미확인입니다.** Supabase 에는 「서버가 이 회원으로 세션을 만들어 달라」는
공개 API 가 없습니다. 알려진 길은 둘이고, **어느 쪽도 이 세션에서 공식 문서로 다시 확인하지
못했습니다**(supabase.com 이 막혀 있습니다) —
1. Admin API `generateLink(magiclink)` 로 일회용 토큰을 만들고 서버가 바로 `verify` 해 세션을
   받는 길 — 메일 주소가 필요해 **우리가 정한 가상 주소**(실제로 메일을 안 보내는)를 씁니다.
2. 프로젝트 JWT 비밀로 서버가 접근 토큰을 직접 서명하는 길 — 새로고침 토큰이 없어 세션
   연장을 따로 만들어야 합니다.
→ 대행사를 고르시면 1번을 먼저 **로컬 Supabase 로 눌러 보고** 정합니다.

## 4. 카카오 계정 ↔ 휴대폰 계정

- ⚠️⚠️ **이름 · 입력한 전화번호로 자동으로 합치지 않습니다.** 같은 사람인지 가르는 것은 **CI 하나**입니다.
- 카카오 계정에는 CI 가 없습니다. 그래서 —
  - **카카오로 로그인한 상태에서** 「본인인증 추가」를 하신 경우에만 그 CI 를 **그 계정에** 답니다(명시적 연결).
  - 휴대폰으로 처음 들어오시면 **새 계정**입니다. 같은 CI 가 이미 다른 계정에 있으면 **그 계정으로** 들어갑니다.
  - 한 CI 는 한 계정에만(`unique`). 두 계정을 합치는 일은 두 계정 모두로 로그인한 상태에서만, 운영자 확인을 거쳐 — **첫 판에는 만들지 않습니다.**

## 5. 필요한 것 — 갈래별

| 갈래 | 내용 |
|---|---|
| **계약** | 본인확인 대행사 1곳(예: PortOne 통합인증 · NICE평가정보 · KCB · 다날 등). 사업자등록 · 통신판매업 신고 · 심사가 보통 필요합니다 |
| **비용** | 대행사 견적(건당 과금 · 월 기본료 여부). **여기 적지 않습니다** — 지어낸 숫자가 됩니다 |
| **발급 정보** | 대행사의 가맹점 id · API 키/비밀 · (화면용) 채널 키 |
| **환경변수(Vercel)** | 대행사 API 비밀, `CI_HASH_PEPPER`(CI 를 HMAC 할 서버 비밀), `SUPABASE_SERVICE_KEY`(지금도 비어 있음 — 사진 기능과 같은 키) |
| **서버 작업** | `api/identity.js`(결과 확인 · 회원 찾기/만들기 · 세션) — 서비스 키는 **서버에만** |
| **DB 변경(새 번호)** | 표 `account_identity` — `user_id`(1:1) · `ci_hash`(**unique**) · `verified_at` · `vendor`. 화면 GRANT · 정책 **없음**(서버만 씀). 성명 · 생년월일 · CI 원문은 **안 담습니다**(같은 사람 판별에 hash 로 충분) |
| **화면** | /login 「휴대폰으로 로그인」 · /my 「본인인증 추가」 — **연동이 실제로 도는 날에만** 냅니다 |
| **법 · 방침** | 개인정보처리방침에 본인확인 대행사(수탁자) · 받는 항목 · 목적 · 보유 기간을 **같은 날** 적기. CI 처리 근거 확인 — 변호사 확인 권장 |

## 6. 계약 없이 지금 한 것 / 안 한 것

- **한 것:** 이 정리, 카카오 하나로 로그인 정리(같은 날), 기존 메일 회원 현황 확인.
- **안 한 것:** 서버 코드 뼈대. 대행사마다 인증창 SDK · 결과 확인 API · 응답 꼴이 달라서, 고르시기 전에
  짜면 고를 때 버리게 됩니다. 고르시면 그 대행사의 **시험 계정(sandbox)** 으로 로컬에서 끝까지 눌러 보고 올립니다.
